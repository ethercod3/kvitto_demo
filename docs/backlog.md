# Backlog: API платежей «Квитто»

Источник требований: `docs/Тестовое_Junior_Python_FastAPI.pdf`.

Цель — реализовать небольшой, полностью запускаемый и протестированный API приема платежей на FastAPI. В план включены все обязательные требования и все бонусы из ТЗ.

## Принятые технические решения

- Python 3.11+, FastAPI, Pydantic v2.
- PostgreSQL как основная база, SQLAlchemy 2.x async и Alembic. SQLite можно оставить только как быстрый тестовый адаптер, если это не усложнит код.
- Суммы хранятся и передаются только целыми копейками (`int`), без `float`.
- Идемпотентность обеспечивается уникальным ограничением БД на `idempotency_key`, а не только проверкой в коде.
- Статусы платежа: `pending`, `succeeded`, `failed`, `refunded`; допустимы только переходы `pending -> succeeded`, `pending -> failed`, `succeeded -> refunded`.
- Подпись вебхука вычисляется как HMAC-SHA256 от исходного тела запроса с секретом `WEBHOOK_SECRET` и передается в `X-Signature`.
- API возвращает даты в ISO 8601, UUID — строкой, суммы и элементы графика — целыми числами.

- [ ] Создать структуру приложения: `app/main.py`, `api/`, `models/`, `schemas/`, `services/`, `db/`, `core/` и `tests/`.
- [ ] Описать зависимости в `pyproject.toml`: FastAPI, Uvicorn, SQLAlchemy, asyncpg, Alembic, pydantic-settings; для разработки — pytest, pytest-asyncio, httpx и ruff.
- [ ] Добавить настройки через переменные окружения: `DATABASE_URL`, `WEBHOOK_SECRET` и параметры приложения.
- [ ] Добавить безопасный `.env.example`; реальные `.env` и локальные артефакты включить в `.gitignore`.
- [ ] Настроить создание приложения, подключение роутеров и lifecycle базы данных.
- [ ] Добавить единый репозиторный файл правил для ИИ `AGENTS.md` с командами запуска, тестирования, линтинга и архитектурными ограничениями.

Критерий готовности: приложение импортируется, `/docs` открывается, конфигурация читается из окружения, секреты не попадают в репозиторий.

## Этап 2. Модель данных и миграции

- [ ] Создать модель `Tariff`: `id`, `code`, `title`, `price`.
- [ ] Создать модель `Payment`: UUID `id`, `status`, `tariff_id`, `amount`, `discount`, `method`, nullable `installment_months`, nullable JSON-массив `schedule`, `email`, nullable `idempotency_key`, `created_at`.
- [ ] Добавить enum/ограничения для способов оплаты `card`, `sbp`, `installment` и статусов платежа.
- [ ] Добавить уникальные ограничения на код тарифа и непустой `idempotency_key`, индексы для `email`, `status` и `created_at`.
- [ ] Настроить Alembic и создать первую миграцию схемы.
- [ ] Реализовать идемпотентный seed тарифов при старте/отдельной командой:
  - `basic` — `990000` копеек;
  - `standard` — `1990000` копеек;
  - `premium` — `2990000` копеек.
- [ ] Проверить миграцию на чистой PostgreSQL и повторный запуск seed без дублей.

Критерий готовности: `alembic upgrade head` создает схему, три тарифа появляются ровно по одному разу.

## Этап 3. Доменные правила

- [ ] Реализовать расчет цены: исходная цена тарифа, скидка `10%` для промокода `KVITTO10` без учета регистра, итоговая сумма в копейках.
- [ ] Неизвестный промокод отклонять с HTTP 422.
- [ ] Для `installment` требовать `installment_months` только из набора `3`, `6`, `12`; для остальных способов не принимать срок рассрочки.
- [ ] Реализовать график рассрочки без дат: базовая часть `amount // months`, остаток `amount % months` по одной копейке добавляется к первым платежам.
- [ ] Для `card` и `sbp` сохранять и возвращать `schedule: null` и `installment_months: null`.
- [ ] Реализовать централизованную проверку переходов статуса; запрещенный переход не должен менять запись.

Критерий готовности: бизнес-правила вынесены из роутеров в тестируемые функции/сервисы, ни в расчетах, ни в базе нет `float`.

## Этап 4. Обязательные API-эндпоинты

- [ ] `GET /tariffs`: вернуть HTTP 200 и список объектов `{id, title, price}`.
- [ ] `POST /payments`: принять `tariff_id`, `email`, `method`, опциональные `installment_months` и `promo_code`.
- [ ] При создании платежа проверить тариф, промокод и способ оплаты; рассчитать `discount`, `amount` и `schedule`; сохранить платеж со статусом `pending`; вернуть HTTP 201.
- [ ] Поддержать заголовок `Idempotency-Key`: первый запрос создает платеж, повторный с тем же ключом возвращает исходный платеж с HTTP 200.
- [ ] Обработать конкурентные запросы с одинаковым ключом через уникальное ограничение и повторное чтение существующей записи.
- [ ] `GET /payments/{id}`: вернуть платеж с HTTP 200 либо HTTP 404.
- [ ] `POST /webhooks/bank`: принять `payment_id` и `status`, найти платеж, проверить переход, обновить статус и вернуть HTTP 200 `{"result": "ok"}`.
- [ ] Для отсутствующего платежа в вебхуке вернуть HTTP 404; для запрещенного перехода — HTTP 409 `{"error": "invalid_transition"}` без изменения статуса.
- [ ] Сохранить стандартный формат FastAPI для ошибок валидации HTTP 422.
- [ ] Во всех ответах платежа вернуть: `id`, `status`, `tariff_id`, `amount`, `discount`, `method`, `installment_months`, `schedule`, `email`, `created_at`.

Критерий готовности: контракты видны в OpenAPI, коды ответов и тела совпадают с ТЗ.

## Этап 5. Бонусные API-возможности

- [ ] Проверять `X-Signature` у `POST /webhooks/bank`: HMAC-SHA256 от необработанных байтов тела с `WEBHOOK_SECRET`, сравнение через `hmac.compare_digest`, неверная или отсутствующая подпись — HTTP 401.
- [ ] Добавить `GET /payments` с независимыми фильтрами `email` и `status`, поддержать их совместное применение.
- [ ] Добавить стабильную сортировку списка платежей по `created_at`, затем по `id`; ограничить размер ответа через `limit`/`offset`, если это не расходится с проверками ТЗ.

Критерий готовности: подпись нельзя обойти изменением тела, фильтры корректно работают отдельно и вместе.

## Этап 6. Автотесты

- [ ] Проверить неизвестный промокод и стандартный ответ HTTP 422.
- [ ] Параметризовать график рассрочки для 3, 6 и 12 месяцев: длина верна, элементы целые, сумма элементов точно равна `amount`, остаток находится в первых платежах.
- [ ] Проверить обязательность и допустимые значения `installment_months`.
- [ ] Проверить повторный запрос с тем же `Idempotency-Key`: HTTP 200, тот же `id`, в базе одна запись.
- [ ] Проверить конкурентный сценарий одинакового ключа, если тестовая инфраструктура позволяет надежно воспроизвести гонку.
- [ ] Проверить каждый разрешенный переход статуса.
- [ ] Проверить запрещенный переход: HTTP 409 и статус в базе не изменился.
- [ ] Проверить HTTP 404 для неизвестного платежа в `GET /payments/{id}` и вебхуке.
- [ ] Проверить корректную, отсутствующую и неверную HMAC-подпись вебхука.
- [ ] Проверить `GET /payments` без фильтров, с каждым фильтром и с обоими фильтрами.
- [ ] Добавить проверки ответов `GET /tariffs` и полного состава полей платежа.

Критерий готовности: `pytest` проходит локально; тесты проверяют результат и состояние БД, а не только HTTP-код.
